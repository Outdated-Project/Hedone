# 渲染与内存

Aurora 是应用内的动效与资源调度层，依托 Flutter 的 SchedulerBinding、Ticker 和渲染树工作。没有修改 Flutter 引擎，也不把一个动画控制器包装成独立渲染引擎。

## 页面与动效

桌面侧栏固定展开，不提供折叠入口。手机（包括横屏）和平板竖屏使用底部胶囊导航；短边至少 600 逻辑像素的移动端窗口在横屏时使用侧栏。判断使用完整窗口尺寸，键盘弹出不会触发导航形态切换。旋转保留当前页面与输入框状态。

主导航共用一个时钟。`AuroraSceneDelegate` 通过 Flow 的 repaint 通知提交位移、缩放与透明度，不在每帧构建或布局页面。空间位移采用 M3E Expressive spatial spring，透明度使用有界效果曲线。快速改选会采样当前位移、缩放、两者速度及透明度，再从当前姿态转向新目标，修复反向切换时的跳变；后台停止时钟，减少动态效果直接到终态。透明度过渡仍可能产生合成层，并不等于没有 GPU 开销。

过渡中的透明度曲线每帧计算一次，可见页面分别采样保留动量的位移和缩放弹簧；弹簧轨迹只在导航改变时创建。到达终态后只绘制当前页面，直接使用单位变换和完整不透明度。没有常驻的刷新定时器，静止页面不为了显示一个 FPS 数字持续提交帧。

页面以不透明的主题背景参与合成，底层页面直接绘制，上层页面按累计权重计算透明度。普通双页过渡只需要一个透明层，避免两张整页同时淡出造成背景透出和额外合成开销。反向切换保留可见页面的叠放顺序；仅完全不可见的新页面放到最上层。回归同时检查实际绘制矩阵、速度衔接、合成权重和透明层数量。

## 系统刷新率

Android 的 `DisplayRefreshPolicy` 在窗口可见且获得焦点时，申请当前分辨率下最高的受支持刷新率，不写入显示模式 ID，也不修改系统设置。省电模式、失焦或进入后台时将窗口偏好恢复为 0，交还系统调度；重新进入前台以及显示器变化后重新计算。系统的温控、用户刷新率限制和厂商调度仍有最终决定权。实现依据 Android 的 [preferredRefreshRate](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#preferredRefreshRate) 窗口接口。

iOS 已启用 `CADisableMinimumFrameDurationOnPhone`。桌面和 Flutter 动画继续使用引擎提供的 VSync，不增加 60 Hz 定时器，也不把视频源帧率当作 UI 刷新率。165、120、90、60 Hz 分别要求每个流水线阶段约在 6.06、8.33、11.11、16.67 ms 内完成；申请高刷不能保证设备始终达到该帧率。

高刷验收必须使用 Profile 或 Release 构建，分别测试系统最高刷新率、省电模式、旋转、后台恢复和外接屏。Android 原生策略已通过发布构建检查，并在 WGRR-W19 平板完成 120 Hz 实测，四轮连续滑动约 113–120 FPS；详情见[平板 ADB 记录](benchmarks/tablet-adb.md)。90/165 Hz 尚无实机结果，省电模式因测试设备正在充电而未能启用，不能据此宣称全部场景满帧。

过渡完成后保留最近两个导航页面；系统内存压力下只保留当前页面。淘汰会释放页面持有的图片监听和结果列表。搜索输入和分类以轻量 PageStorage 状态保留，重新访问已淘汰页面会重新请求数据。正在浏览的分页数据仍随加载增长；本轮没有把它改造成会丢弃历史页的固定窗口。

观看历史、收藏等模型更新不再重建 MaterialApp；外观、震动和服务失效才通知应用外壳。进度更新仍限定在控制区。

封面与详情通过 Hero 连接。飞行期间固定封面解码约束，避免每一帧重新解码不同大小；详情自动播放等到路由入场结束后才创建解码器。现有单播放器、跨集复用、相邻地址预取和后台暂停策略保持有效。

## 高清封面与播放

封面根据实际设备像素比和展示尺寸计算解码目标。`cover` 使用覆盖裁切所需的比例，`contain` 使用完整显示比例，保持原始宽高比，不放大小图。64 像素量化减少窗口拖动产生的重复缓存项；普通卡片上限 1 M 像素，大幅封面上限 3 M 像素。上限限制内存，不代表所有源图片都能显示为原始分辨率。视频解码分辨率不受封面预算影响。

视频和 HLS 分片走 Reqwest 的按需流式响应。每次向网关交付最多 32 KiB；不再先缓冲整段，不再要求上游提供强 ETag 才能读取大文件。Range 原样传给上游，保持同一个响应的内容一致性；不自动拼接多个版本，不在中途失败后重放已交付字节。客户端取消后释放响应与许可。数据读取沿用 20 秒停滞超时，连接超时 8 秒。

媒体传输独立占用最多两个许可，API/图片的四个许可不会被长视频一直占据。普通响应仍限制为 8 MiB。HLS 只缓冲需要改写的清单，最多 2 MiB；错误标注 MIME 的清单也通过内容签名识别，子列表、密钥和初始化段继续经过相同 URL/DNS/TLS 策略。网关不保存流式分片副本。

Flutter 图片缓存为 32 MiB / 96 张，播放器缓冲配置为 8 MiB。两者都不包括全部活跃图片、解码器、GPU 纹理或原生库。Rust 保留封面/清单缓存；旧的有限缓冲工具入口仍有密钥/分片缓存预算，但播放器网关已不走该路径。不得把预算相加当成 RSS 上限。

## 可复现验证

```sh
flutter test --no-pub
cargo test --manifest-path rust/Cargo.toml --features server
flutter drive --driver=test_driver/integration_test.dart --target=integration_test/rendering_profile_test.dart --profile -d windows
```

`rendering_test.dart` 验证动画帧不增加场景 build/layout 次数、页面保活数量、历史通知隔离、cover 裁切清晰度与解码像素预算。Rust 使用真实本地 TCP 测试头部先到、24 MiB 大响应、32 KiB 交付块、无 ETag、取消后许可释放、截断错误、Range 和跨块 HLS 签名。

Profile 场景使用本机 HTTP 返回应用品牌图片作为测试海报，48 条明确的测试记录、20 次导航切换和 4 次滚动，不启动视频解码器。输出记录实际引擎 build/raster 分位数、超 16.67 ms 帧数、系统报告的刷新率、超出对应帧预算的帧数、采样 RSS 与图片缓存。刷新率在 timing 回调时采样，跨越刷新率切换的批次可能存在时差；该统计不是实际呈现 FPS。它隔离 UI 工作，不代表真实视频播放、弱网或低端 Android 性能。

统一滚动位置后的原始报告和完整对照保存在 [docs/benchmarks](benchmarks/README.md)，探索记录位于 `build/qa/rendering-profile-*.json`。没有以桌面测试推导所有设备 120 Hz，也没有 GPU 利用率下降百分比的测量。优化方法参考 Flutter 的[性能实践](https://docs.flutter.dev/perf/best-practices)。
